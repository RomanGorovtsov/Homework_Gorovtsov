## 2. Сильные стороны (что уже хорошо)

### 2.1. Последовательная структура «по урокам»
Пакеты `Lesson3 → Lesson17` образуют читаемую хронологию обучения: по имени пакета понятно, какой теме соответствует код. Для учебного репозитория это осмысленный выбор — история прогресса видна и в git (ветки/PR на каждый урок).

### 2.2. Современный и консистентный стек
- JUnit 5 (Jupiter + platform suite) вместо устаревшего JUnit 4.
- RestAssured 5.x — актуальная мажорная версия.
- Gradle wrapper закоммичен — проект воспроизводится без локальной установки Gradle.
- Зависимости объявлены централизованно в `build.gradle`, есть BOM для JUnit.

### 2.3. Культура юнит-тестирования (Lesson15) — эталонный блок проекта
- `@DisplayName` на русском делают отчёты самодокументируемыми.
- Активно используются параметризованные тесты: `@CsvSource` для граничных значений возраста (`BoardGameTest`), `@MethodSource` со сценариями аренды (`GameRentalTest`).
- Изоляция через `@BeforeEach` — каждый тест получает свежий `GameRental`.
- Покрыты граничные и негативные случаи: `null`, дубликаты, повторная аренда/возврат, несуществующие сущности, проверка исключений через `assertThrows`.
- Имена методов в стиле `shouldXxxWhenYyy` — читаются как спецификация.

### 2.4. Грамотная организация BDD-слоя (Lesson16)
- Feature-файл лежит в `src/test/resources`, шаги — в отдельном классе, glue прописан через аннотации junit-platform-suite. Разделение корректное.
- Шаги покрывают продвинутые приёмы: Data Table, Doc String, Scenario Outline, регулярные выражения в паттернах шагов.

### 2.5. API-тесты (Lesson17): правильные приёмы уже применяются
- Есть **DTO с Lombok** (`Usuario`) — сериализация тела запроса объектом вместо ручного JSON (тест `shouldCreateNewUserFromDto`).
- Покрыт **полный жизненный цикл**: создание → обновление → логин → удаление → проверка, что пользователь больше не найден.
- Есть **отдельный негативный тест-класс** (`ServeRestNegativeTest`) — позитив и негатив не смешаны.
- Свежий рефакторинг ввёл `RequestSpecBuilder` с общим `baseSpec` (baseUri + contentType + логирование), константы сообщений и хелперы для генерации тел запросов — дублирование заметно снижено.

### 2.6. Инженерная гигиена
- `AGENTS.md` фиксирует конвенции проекта (стек, расположение тестов) — полезно и людям, и AI-ассистентам.
- `.gitignore` настроен, история git чистая: ветка/PR на урок, осмысленные сообщения коммитов.

## 3. Точки роста (что можно улучшить)

Приоритезация: 🔴 важно сейчас · 🟡 в ближайшее время · 🟢 когда проект вырастет

### 3.1. 🔴 Дублирование конфигурации между API-тест-классами
`BASE_URI` объявлен отдельно в `ServeRestTest` и в `ServeRestNegativeTest`. Рефакторинг одного класса уже оторвался от второго — общий `baseSpec` есть только в первом.

**Рекомендация:** вынести общую конфигурацию в одно место:

```java
// config/ApiConfig.java или Specs.java
public final class Specs {
    public static final RequestSpecification BASE = new RequestSpecBuilder()
            .setBaseUri("https://serverest.dev")
            .setContentType(ContentType.JSON)
            .log(LogDetail.ALL)
            .build();
}
```

Заодно появится место для параметров окружения (`src/test/resources/env.properties` + `ConfigReader`), чтобы базовый URL не был захардкожен.

### 3.2. 🔴 Упорядоченные тесты со статическим состоянием
В `ServeRestTest` состояние гонится через `static` поля (`userId`, `token`, `uniqueEmail`) и `@Order`. Это скрытая связность: падение `@Order(3)` каскадом роняет 4–6, тесты нельзя запускать параллельно и поодиночке, а зависимость не видна из сигнатур.

**Рекомендация:** сделать тесты независимыми — создание пользователя в `@BeforeEach`, удаление в `@AfterEach`; токен получать там же. Ordered-сценарий допустимо оставить как один E2E-смоук, но не как основной стиль API-тестов.

### 3.3. 🟡 Нет слоёв в API-тестах: эндпоинты и клиенты
Пути `/usuarios`, `/login`, `/produtos` размазаны строками по методам. При росте числа тестов это превратится в проблему переименования.

**Рекомендация (поэтапно):**
1. Константы эндпоинтов (`Endpoints.USUARIOS`).
2. Тонкий клиентский слой: `UserService.create(...)`, `UserService.login(...)` возвращают `Response` — тесты перестают знать про HTTP-детали.
3. Отдельный пакет `models/` для DTO (сейчас `Usuario` живёт в `src/main`, что смешивает учебный домен и тестовую инфраструктуру).

### 3.4. 🟡 Организация пакетов отражает хронологию, а не тип тестов
Сейчас невозможно запустить «только API» или «только BDD» одной командой.

**Рекомендация:** добавить теги — `@Tag("api")`, `@Tag("unit")`, `@Tag("bdd")` — и фильтровать через `./gradlew test --tests org.example.Lesson17.*` либо task'ами в `build.gradle`. Перекладывать пакеты физически не обязательно, теги дешевле.

### 3.5. 🟡 Cucumber-шаги только печатают в консоль
Все шаги `BookingSteps` завершаются `System.out.println` — сценарии ничего не проверяют и всегда «зелёные». Для урока про синтаксис Gherkin это нормально, но как шаблон опасен.

**Рекомендация:** подключить шаги к реальной модели (например, домену из Lesson15) и заменить печать на ассерты состояния. Заодно вывести логирование на SLF4J вместо `System.out`.

### 3.6. 🟡 Не зафиксирована версия Java
В `build.gradle` нет `sourceCompatibility`/toolchain — сборка зависит от JDK машины. На другом JDK поведение компилятора/варнингов может отличаться (что уже видно по предупреждениям Gradle 9 о native access).

```groovy
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}
```

### 3.7. 🟢 Гигиена зависимостей
Версии разрозненны по эпохам (Cucumber 7.15, JUnit BOM 5.10, Jackson 2.22). Стоит перенести их в version catalog (`gradle/libs.versions.toml`) — единая точка правды и меньше конфликтов при апгрейде. Также стоит ревизировать зависимости, которые могли остаться от старых уроков.

### 3.8. 🟢 Нет README и CI
- **README.md**: как запустить (`./gradlew test`, фильтры по классам/тегам), какая нужна JDK, краткая карта уроков.
- **CI**: при уже сложившемся flow «ветка → PR на урок» GitHub Actions с прогоном `./gradlew test` на каждый PR даст регрессионную защиту почти бесплатно.

### 3.9. 🟢 Отчётность
Дефолтных HTML-отчётов JUnit на старте достаточно, но естественная следующая ступень для API-проекта — **Allure** (+ `allure-rest-assured` фильтр): шаги, вложенные запросы/ответы, история.

## 4. Итог

Проект демонстрирует уверенную восходящую траекторию: юнит-блок Lesson15 — сильнейший по качеству (параметризация, граничные случаи, изоляция), API-блок Lesson17 после рефакторинга движется в ту же сторону (спеки, константы, DTO, негативные сценарии).

**Три приоритета на ближайший шаг:**
1. Общая конфигурация RestAssured для всех API-тестов (устранить дубль `BASE_URI`).
2. Избавиться от `@Order` + статических полей в пользу независимых тестов с `@BeforeEach`/`@AfterEach`.
3. Закрепить toolchain в `build.gradle` и добавить README.

Эти изменения небольшие, но именно они превращают набор уроков в проект, который масштабируется без боли.
